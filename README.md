# ExcelTrainingMonitor

ExcelTrainingMonitor is a Windows desktop app for managing training-status spreadsheets. It started as an Excel monitor, but it now also includes a GridBook editor so the app can create, edit, save, export, monitor, and report on spreadsheet data from one themed interface.

## What It Does

- Monitors an Excel `.xlsx` file for training status changes.
- Shows one scrollable notification for open training items instead of many separate popups.
- Shows a separate update notification when the Excel file changes.
- Tracks persistent history in local app data.
- Provides a GridBook Editor tab for creating and editing spreadsheet-style sheets.
- Saves GridBook edits back to `.xlsx`.
- Exports training data to Excel and CSV.
- Prints grid and pie-chart reports through the Windows print dialog, including Microsoft Print to PDF.
- Exports pie charts as PNG images.
- Supports reminder dates/times and optional ntfy.sh notifications for phones and email.
- Can start a lightweight reminder agent when the main window closes.

## Repository Layout

- `src/` contains the WinForms application source.
- `build.bat` builds source packages and release packages from scratch.
- `installer/` contains the optional Inno Setup installer script.
- `artifacts/` is generated by `build.bat` and is ignored by Git.

Built executables should not be committed with the source. The build script creates release output under `artifacts/release/` so the repository stays source-first.

## Build Requirements

To build from source on Windows, install:

- Windows 10/11 x64
- .NET 8 SDK or newer from https://dotnet.microsoft.com/download/dotnet/8.0
- Windows PowerShell, included with Windows
- Internet access for the first NuGet restore, because the project uses ClosedXML
- Optional: Inno Setup from https://jrsoftware.org/isdl.php if you want an installer `.exe`

The release ZIP is self-contained, so normal users should not need to install .NET to run the built app.

## Build From Scratch

Open a terminal in the repository root and run:

```bat
build.bat
```

The script checks required build dependencies first. If something is missing, it prints what is missing and where to get it.

Each successful build increments the patch version in `version.txt` and updates the project version metadata.

On success it creates:

- `artifacts/release/ExcelTrainingMonitor_<version>_<timestamp>/`
- `artifacts/release/ExcelTrainingMonitor_<version>_<timestamp>.zip`
- `artifacts/source/ExcelTrainingMonitor_source_<version>_<timestamp>.zip`
- `artifacts/installer/ExcelTrainingMonitorSetup-<version>.exe` when Inno Setup is installed

The release ZIP contains the built self-contained app. The source ZIP contains a clean source package without build outputs, `.git`, or generated artifacts.

## Portable App Or Installer?

The portable ZIP is enough for most users. It contains the self-contained app, including the .NET runtime files needed to run it.

The installer is optional. It is useful when you want:

- A normal installation under Program Files or the user app folder
- Start Menu and Desktop shortcuts
- A Windows uninstall entry
- A more familiar experience for non-technical users

The project supports both. Keep the portable ZIP as the main GitHub Release asset and publish the installer as an extra asset when you want an installable experience.

## Release Workflow

Recommended workflow:

1. Commit source changes to GitHub from the repository.
2. Run `build.bat` locally or in CI.
3. Create and push a version tag, for example `v1.0.31`.
4. GitHub Actions builds the release assets and creates the GitHub Release from the tag.
5. Upload local Visual Studio builds manually only when you intentionally want to bypass the automated workflow.
6. Use the source ZIP only when you need a clean source/pipeline archive.

The included workflow is `.github/workflows/release.yml`. It runs on tags matching `v*` and can also be started manually from the GitHub Actions tab.

Do not put release folders or built `.exe` files inside `src/`. If a built executable is already committed beside the source, remove it from Git and let `build.bat` recreate it.

## Should Dependencies Be Included?

For the release ZIP: yes, as much as practical. The app is published as a self-contained Windows x64 build, so the .NET runtime is bundled into the release output. That is better for end users because they can download and run the app without installing the .NET runtime separately.

For the source/pipeline ZIP: no. Source packages should not include NuGet packages, compiled binaries, `bin/`, `obj/`, or release folders. Builders should restore packages with `dotnet restore`, which `build.bat` already does.

## Notes

- ntfy.sh notifications require a topic and optional email configured in the app.
- The background reminder agent uses the same executable with `--reminder-agent`.
- History is stored under the current user’s local app data folder.
